## Opt-in contract and temporary lifecycle choice

```text
yetlet new NAME --framework-path PATH --assets vite --with-vite-dev
```

All eight cloud/config/Tailwind combinations are supported by the new parse and
scaffold path. Without the new flag, the existing `Cli::New` / `Cli::NewVite`
results, APIs, inventories and generated bytes are preserved. The opt-in output
adds exactly two root files to YT-099: `vite.dev.config.mjs` and
`vite.dev.bridge.mjs`. Only `package.json` gains a dev script and README gains
an introductory dev section. Generated Rust `src/main.rs` / `src/vite.rs`, every
other production file and both npm locks remain identical to the corresponding
production-only profile. No arbitrary subdirectory support was introduced.

Build dist explicitly once before starting: Rust still validates and snapshots
its production manifest before listening. Terminal A runs the existing native
foreground `yetlet dev --manifest-path APP/Cargo.toml` with operator-selected
absolute `YETLET_ASSET_ROOT` and Rust fixed at `127.0.0.1:3000`. Config/cloud
host/port selection and backend-only token remain terminal A responsibilities.
Terminal B runs `npm run dev` in the app root. It uses pinned Vite 8.3.4 at
`127.0.0.1:5173`, with strictPort and optional exact `YETLET_VITE_PORT`
1024–65535 excluding 3000. No process supervisor or automatic Vite startup is
added. Each terminal owns its foreground process and must be stopped explicitly.
Live signal/stop/restart behavior is still unverified in this sandbox.

The application-owned Node bridge forwards only read-only root HTML from fixed
HTTP `127.0.0.1:3000/`. No target, path, cookies or client credentials can select
an upstream. A three-second overall deadline and 256 KiB response bound fail
closed to a plain-text no-store/nosniff 503. It requires successful HTML with
the exact production CSP and exact generated root head/asset/image markup.
Only that production asset block and the one `#local-mark` SVG URL change.
Rust-rendered escaped body content is preserved. Other Rust routes/actions are
outside this deliberately narrow development profile.

Each dev HTML response gets an 18-byte cryptographic random nonce, the Vite
client and `/app.ts` module entries, and `meta[property=csp-nonce]`. CSP changes
only `style-src` by that nonce and `connect-src` by the exact loopback WebSocket.
No unsafe-inline/eval, data, wildcard, external font/CDN or backend header is
introduced. Vite's installed client reads that meta nonce for CSS HMR styles;
actual DOM/computed-style/WS proof remains outstanding. The local SVG is rewritten
to the same explicit Vite origin used by its frontend asset import.

The dev config imports the unchanged production config, overrides only the
explicit development profile, uses `server.ws` host/port settings and refuses
listener CLI overrides. Host/origin checks additionally protect HTTP and WS;
`allowedHosts: []`, exact CORS origin, `fs.strict`, app-root-only `fs.allow`,
sensitive-file denial, `envDir: false` and `publicDir: false` are configured.
A finite public source-path allowlist blocks configs, secrets, locks and raw
filesystem access except Vite's one internal env module. Frontend imports and
intentionally referenced VITE variables are public: never put secrets there.
No Node/Vite/browser dependency enters core, the normal CLI or Rust runtime.

The implementation follows the official [Vite backend integration guide](https://vite.dev/guide/backend-integration)
and [server options](https://vite.dev/config/server-options), also checked
against the installed 8.3.4 client and type definitions. The two-terminal choice
is a bounded development arrangement, not a fundamental framework architecture
change or an automatic multi-platform lifecycle guarantee.
