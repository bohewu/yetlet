## Established behavior and application amplification

The failed full synchronized attempt captured twelve WAL `fsync` calls >=100 ms across rounds 2/3. Seven round-3 calls lasted 505–508 ms; round-3 write p95 was 548.889 ms and 183/1,500 writes were >=500 ms. The calls returned successfully. This was latency, not an HTTP/SSE error or reported I/O failure.

`Database::run` in `examples/lab-operations-board/src/database.rs` holds the single connection mutex throughout each operation, including `save`'s transaction commit. The four-worker admission semaphore does not provide four independent database connections. A slow commit therefore holds up the other admitted workers and queued requests. The synchronized helper produces a wave of 25 writes every approximately ten seconds. A roughly 506 ms flush followed by the remaining ordinary ~3 ms serial commits is consistent with the observed 548.889 ms write p95 and 585.186 ms maximum. The earlier retained 75-second diagnosis also associates a 497.406 ms WAL sync with a 25-write episode at 499.379–582.061 ms. This explains queue amplification; it is not proof of an exact syscall-to-request mapping in the newer full run, whose raw request rows lack individual wall timestamps.

The long calls are not themselves the visible checkpoint sync sequences. In `full-sync-20261013T074209233775Z/fsync-start-2.trace`, the 383.148 ms call at line 3525 returns before ten ordinary WAL syncs, then a separate 0.905 ms WAL sync and 3.112 ms main-database sync at lines 3536/3537. The 443.140 ms call at line 3678 is followed by an ordinary 3.017 ms WAL sync, then separate 0.880 ms WAL and 2.868 ms database syncs. The seven >=500 ms calls have their next main-database sync 20–40 seconds later. Nearby checkpoint timestamps must not be treated as proof that checkpointing caused the long syscall. This does not exclude every indirect effect of checkpoint or shared storage activity.

The helper has no sixty-second pacing action in its data-request loop. The application's bundled SQLite automatic checkpoint is page-count driven, not a minute timer. Observed stalls at every sixth ten-second wave do not by themselves distinguish a time-based trigger from an operation-count trigger sampled at that cadence. [SQLite WAL documentation](https://www.sqlite.org/wal.html) describes the checkpoint threshold and FULL commit synchronization.
