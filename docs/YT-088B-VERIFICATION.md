## Windows implementation and API decision

Only ordinary absolute/relative drive paths on **local fixed NTFS** are accepted. UNC, device/verbatim namespaces, parent traversal, reparse objects, ADS, reserved device components, trailing-dot/space ambiguity and non-Unicode paths fail closed. Spaced and Unicode paths/content use UTF-16 OS names and the unchanged UTF-8 template bytes.

The volume root is opened with documented `CreateFileW`, `FILE_FLAG_BACKUP_SEMANTICS` and `FILE_FLAG_OPEN_REPARSE_POINT`. Every subsequent component is opened relative to its held predecessor through `NtCreateFile(FILE_OPEN)`, with `FILE_OPEN_REPARSE_POINT` and `OBJ_DONT_REPARSE`. Every ancestor denies delete sharing; every selected link is reopened and compared against its original volume/file ID. Directory handles share write because the documented native rename target-directory open requires it. No later operation reconstructs a parent DOS path for traversal. A pre-existing delete-capable opener causes a sharing refusal before staging.

The task-owned stage is created and opened in **one** `NtCreateFile(FILE_CREATE)` call relative to the pinned parent. An explicit owner/current-user-only protected inheritable DACL is supplied in that same call. This is the selected native handle-relative creation alternative to checking a parent ACL and then calling mkdir/open; there is no directory-entry substitution window between creation and ownership acquisition. The parent may permit unrelated entries, but the stage's held no-delete-share handle and private DACL protect its ownership and contents. Other processes running as the same user, administrators and kernel drivers are not a sandbox boundary, consistent with the existing Linux ownership policy.

Publication uses SDK `NtSetInformationFile(FileRenameInformation)` with a zeroed `ReplaceIfExists=false`, the held destination parent as `RootDirectory`, and a single UTF-16 component. The native API was selected instead of assuming that a path-based Win32 rename wrapper preserves relative-root semantics. No replacing rename or precheck-plus-rename fallback exists. NTFS rename is same-volume. Descendant handles are closed before renaming the stage; its private DACL remains in force. Only a successful native rename transfers ownership. A failed/ambiguous result is nonzero and never triggers deletion of the destination.

Rollback marks only exact owned handles for deletion. After descendant handles were closed for publication, rollback reopens names relative to the held private stage/src, verifies original volume/file IDs and refuses foreign substitutions. Unknown entries are never enumerated for deletion. Cleanup failure reports retained staging instead of recursively deleting it. Handles use `File`/`OwnedHandle` RAII; SDK LocalAlloc outputs have a small LocalFree owner. All native entrypoints come from cached `windows-sys`, with no manual FFI declarations or shell fallback.

Current primary SDK references consulted during implementation: [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [NtCreateFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile), [OBJECT_ATTRIBUTES and OBJ_DONT_REPARSE](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes), [FILE_RENAME_INFORMATION relative-root, sharing and no-replace rules](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information), [NtSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile), and [volume-by-handle information](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew). These references justify the API selection; they do not replace native execution evidence.
