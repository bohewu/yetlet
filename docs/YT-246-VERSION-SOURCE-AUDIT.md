# YT-246 — Canonical version authorities and release-document synchronization

Date: 2026-11-09. Status: **Implementation complete; independent Reviewer PASS**.

## Problem and decision

The SDK, CLI, published distribution and public reader edition have different
lifecycles. Treating them as one global "current version" would incorrectly
promote a development checkout or silently move the independently versioned CLI
to a new SDK. Each value therefore has one explicit authority and a fail-closed
synchronization/check path.

| Value | Canonical authority | Rule |
|---|---|---|
| SDK source/package version | Root `Cargo.toml` → `[workspace.package].version` | Shared by `yetlet` and `yetlet-browser` in the current source tree |
| SDK path dependency versions | The same SDK workspace version, only when `path` resolves to one of the two SDK crates | Do not infer package identity from a dependency alias/name alone |
| CLI source/package version | `tools/yetlet-cli/Cargo.toml` → `[package].version` | Independent from the SDK version |
| SDK pin generated by CLI | `tools/yetlet-cli/Cargo.toml` → `[dependencies].yetlet.version` | Independent consumer binding; do not advance automatically with the SDK checkout |
| Actually published SDK/CLI versions | Accepted publication sections in the versioned SDK and CLI release records | Distribution truth; development manifests do not prove publication |
| Public reader edition | `site/pages.toml` → `[edition]` | Explicit consumer decision; does not automatically follow source or publication changes |

## Implemented synchronization contract

Run `python3 scripts/release_docs.py sync` before the read-only release-doc gate.
The shared `scripts/release_version_authority.py` reads accepted publication
records for both the release checker and the synchronizer.

The synchronizer:

- Audits tracked and untracked Cargo manifests, binds each SDK path dependency to
  its exact TOML table and alias, and verifies the declared package identity and
  resolved crate path before adding/updating version constraints. Only single-line
  inline dependency tables are rewritten; nested/multiline or ambiguous declarations
  fail closed. Registry-only dependencies and unrelated packages are not rewritten.
- Derives SDK package README versions and local/registry examples from the SDK
  workspace manifest.
- Derives the CLI README release field, generated SDK pin, install command and
  expected `yetlet --version` output from the CLI manifest and its SDK dependency.
- Checks both docs-site SDK registry pins against the explicit `site/pages.toml`
  edition. A mismatch fails synchronization/check without rewriting the registry
  manifest; reader-facing first-app text still follows the selected edition.
- Derives current published-version claims in API, capability, compatibility,
  component, documentation-scope and integration guides from accepted release
  records. Module-guide SDK labels and SDK dependency examples follow the source
  workspace version.
- Leaves feature-introduction statements (for example, YT-220/221 being available
  since SDK alpha.6), dated evidence, accepted publication records, the CLI's
  independently selected SDK dependency, docs-site registry manifest and
  `site/pages.toml` untouched.

The sync computes all changes before writing and is idempotent. It does not
rewrite Cargo.lock files; run the normal locked metadata/lock reconciliation
after any manifest version change.

`tools/build_docs.py` now consumes the edition passed from `site/pages.toml`
directly; the duplicated `PUBLISHED_EDITION` constant has been removed.
`examples/docs-site/prepare.py` independently requires both SDK packages to
match that selected edition. The release-doc check also invokes the canonical
version-source check, so stale current values block the release gate.
