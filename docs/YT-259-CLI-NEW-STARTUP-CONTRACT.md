## SDK selection and startup capability

Keep `sdk-latest-v2` / `latest-semver` as the SDK selection identity. A default
request selects the greatest canonical SemVer, including prereleases, with the
non-yanked package set required by the starter. An explicit `--sdk-version`
selects the requested canonical exact SemVer without build metadata. Preserve
the post-selection checks for required package features and equal-version
Browser dependency admission. An incompatible selected version ends creation.
Online refreshes or revalidates the required registry metadata and reports an
online failure if that refresh fails. Explicit offline (`--offline` or
`CARGO_NET_OFFLINE=true`) uses the existing complete local metadata and Cargo
caches without network, with the existing source and age notices. Keep exact
registry manifest pins, protected staging and root lock validation. `new`
performs bounded lock generation and writes a new project. Subsequent build,
run and watch use the generated lock without resolving the app SDK again.
[ADR 0010](adr/0010-dynamic-sdk-version-resolution.md) · [YT-247 contract](YT-247-SDK-VERSION-RESOLUTION-CONTRACT.md) · [YT-247 implementation history](YT-247-SDK-VERSION-RESOLUTION-IMPLEMENTATION.md) · [CLI contract](CLI-CONTRACT.md)

The complete initial source policy adds a required `scaffold_capabilities`
object to the existing resource.

```json
{
  "revision": "sdk-latest-v2",
  "selection": "latest-semver",
  "scaffold_capabilities": {
    "m26_startup": []
  }
}
```

- Each future `m26_startup` row has exactly `sdk_version` and `yetlet_sha256`.
  `sdk_version` follows the same canonical exact rules as `--sdk-version`.
  `yetlet_sha256` is the 64-character lowercase hexadecimal SHA-256 of the
  published core `.crate`. Reject unknown or duplicate keys at every level,
  duplicate versions even with identical checksums, missing fields, invalid
  types, noncanonical versions and invalid digests. Reject malformed policy as
  `SDK_METADATA_INVALID` on every `new` request before rendering or staging.
- The first published M26 version is unknown. Start with an empty array. A
  future entry requires accepted publication, archive readback matching the
  registry index checksum, and actual locked registry-only compile evidence
  for the M26 generated source and the documented `serve_on` path for that
  exact version. The published core package must provide the methods, the
  curated prelude and the resolved-state `App::from_router` path. The Browser
  package pair keeps its existing independent checks. Record the publication
  and compile evidence for each added row. A Cargo feature such as
  `server-axum` establishes a feature graph. An exact archive and its consumer
  compile establish which Rust APIs that release actually provides.
- The first row records the introduction. Each further row independently
  establishes support for its exact version and bytes. SemVer ordering alone
  cannot establish the presence of particular methods or modules in an
  unverified later release. Rows determine scaffold capability after SDK
  selection, so an unlisted latest version remains eligible. An unlisted
  version selects the existing Axum startup for simple Native variants on
  that same version. Exact alpha.7 and currently published earlier versions
  therefore retain legacy-compatible source, with no `serve`, `serve_on` or
  curated prelude emitted. Preserve existing feature compatibility errors.
- After resolution, compare a matching row against the selected core
  package's index checksum, including on offline, Browser and advanced
  requests. A contradiction between the packaged policy and the selected
  package identity is invalid provenance for any selector. A valid match
  changes the template only for the simple Native branches below. When a
  matching row conflicts with the resolved checksum, or the selected M26
  branch cannot compose the required built-in source, assets and matching
  manifest, report `SDK_INCOMPATIBLE` with `template-capability`, the exact
  SDK version, selector, policy identity and reason. Leave the new destination
  absent and preserve any existing destination. End the request without
  retrying an older SDK or emitting the legacy branch for that claimed simple
  profile. Keep existing Cargo lock error codes for lock failures. Validate the
  built-in branch through bounded composition and its existing template
  invariants. Actual Rust API/compile proof comes from Phase C and the later
  registry consumer. Creation continues to run lock generation only.
- Production uses the compiled resource. Tests inject raw policy and registry
  fixtures through the existing internal test seams, with no user-facing
  override. Hash the same raw bytes used to parse the policy for both
  `sdk.policy_sha256` and resource identity checks, including fixture receipts.
  No new dependency, network probe, public Cargo feature or policy cache is
  needed. An SDK selection policy revision still describes version selection.
  The digest distinguishes the exact packaged capability policy bytes.
