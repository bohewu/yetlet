## 5. YT-066b — Separate async provider, no Memory migration

Keep `yetlet-session`, `SessionManager<T>` and `Session<T>` unchanged. Do not force an async return type, rename them merely for symmetry, add `SessionConfig::distributed(true)`, or use `block_on` to disguise network I/O.

The candidate is a separately selected `yetlet-session-redis` crate with `RedisSessionManager<T>` / `RedisSession<T>`, or an application integration that demonstrably satisfies the same requirements. Names and signatures remain illustrative until the first real prototype is reviewed:

```rust
// Existing Memory API remains synchronous.
let value = memory_session.read()?;
memory_session.try_update(|state| mutate(state))?;

// Candidate Redis API exposes network I/O through the type and .await.
let value = redis_session.read().await?;
redis_session.try_update(|state| mutate(state)).await?;
```

Use familiar Rust method naming; do not mechanically add `_async` suffixes. Similar method names do not imply identical error, allocation, latency or consistency behavior. Follow ecosystem conventions by default, but document evidence when compatibility, safety or small explicit design requires a deviation.

Use a mature Redis client and its supported bounded connection/pooling facilities; do not implement a wire protocol, driver or pool. During the design/prototype stage, inspect current official client/pool and existing Session-library documentation/source, including MSRV, cancellation/retry behavior and concurrent updates. Compare a direct thin provider with an existing integration using actual semantics and dependency cost. This planning round deliberately selects no crate/version from memory. Extract shared traits only after a real implementation demonstrates common operations; do not introduce `SessionStore<T, Backend, Serializer, Transaction, ...>` first.

Redis/serialization/pool dependencies must remain absent from Core, the default server facade, browser/WASM and the existing Memory provider. Explicit server-side application composition selects the provider and middleware scope. Do not introduce a second router, global service locator, ORM or automatic fallback provider.

## 6. Redis semantic contract and error model

Start with three application processes sharing **one Redis primary**, with no replica reads or cross-request positive Session cache in the first proof. This reduces the initial consistency surface; it is not Redis HA or Cluster qualification. The store representation needs opaque unpredictable identity, record/schema version, concurrency version, typed serialized state, CSRF and absolute expiry. Set explicit record-size, capacity/admission and pool/queue limits; do not promise an exact global capacity merely from per-record TTL.

| Operation/boundary | Required behavior |
|---|---|
| Create/load | Allocate identity only through the provider; never adopt a supplied unknown identity as authenticated state. Distinguish an absent cookie from a presented invalid/expired/revoked identity and document anonymous-session creation separately. |
| Read | Read an authoritative, unexpired versioned record. Revoked identity must not authenticate on another instance after the successful revocation boundary. Already admitted in-flight application effects are not retroactively undone. |
| `try_update` | Read a versioned snapshot, invoke the synchronous `FnOnce` callback at most once on a candidate, serialize within bounds and compare-and-set once. Return success only after acknowledged commit. A same-version race has one successful commit and one explicit conflict; never silently lose a successful dependent mutation. |
| Application failure | Return the typed application error without committing candidate state. This does not roll back external side effects performed by the callback; document that limitation. Never automatically replay the callback. |
| Rotation/replacement | Atomically validate current identity/version/expiry, retire the old identity, create the replacement and handle CSRF/expiry. Plain rotate preserves successful updates ordered before it; `replace_and_rotate` intentionally replaces state. A racing stale operation fails rather than resurrecting or overwriting retired state. |
| Destroy/revocation | All subsequent authoritative operations reject the old identity on every instance. Updates must require an existing matching record, not upsert a missing retired record. Document the generation/tombstone or equivalent no-resurrection strategy and its lifetime. |
| TTL | Use one authoritative time/expiry policy across workers. Preserve absolute-expiry semantics; ordinary updates must not accidentally refresh expiry. Document rotation's new lifetime and test the actual store behavior. |
| Store failure | Fail closed for Session-dependent routes. Do not authenticate from a stale cache, mint substitute authenticated state, or silently fall back to Memory. Stateless routes outside the provider scope should remain independent. |
| Timeout/cancellation | One overall deadline includes queue, pool acquisition, I/O and any safe retry. Cancellation after command dispatch may leave a committed operation; it is not proof of rollback. Keep capacity occupied until underlying work is completed or safely reaped. |
| Serialization/version | Reject corrupt, oversized and unsupported records with redacted errors. Specify schema compatibility/upgrade rejection; do not silently reset authenticated state or guess a migration. |

The provider's proposed error vocabulary must distinguish application rejection, CAS conflict, expired/revoked identity, invalid record, store unavailability, definite pre-dispatch timeout and **outcome unknown** after an ambiguous write. Exact Rust enum names are deferred; these distinctions are not. Existing Memory errors and method signatures must not be expanded just to imitate Redis.

Do not blindly retry a mutating network operation after an uncertain response. A later bounded retry/reconciliation is allowed only when a reviewed operation identity or equivalent mechanism proves it cannot duplicate mutation or revive an identity. A connection manager's automatic reconnect is not permission to replay arbitrary application work. HTTP mapping remains explicit application policy, with no raw Redis errors or secret-bearing payloads exposed.

### Required design proof: response ordering is separate from store atomicity

Test both a stale request that reaches response finalization after rotation and an older response whose cookie header was already prepared but is delivered after the replacement response. Also test stale destroy/clear and competing rotations across instances. Assert both server rejection of retired IDs and the resulting cookie jar's replacement identity.

A final store check alone cannot retract a header already sent or queued. Redis CAS therefore does not, by itself, prove the requested stale `Set-Cookie` guarantee. The first prototype must establish a bounded cookie issuance/versioning strategy compatible with the SSR-first design, and test forced delivery order with a real HTTP cookie jar. Do not silently weaken the guarantee, add mandatory client JS, or call the provider Done because only retired-ID authentication was rejected. An unresolved cookie-ordering design blocks the full provider stage, not the independent Docker/Memory slice. Existing Memory tests cover their recorded stale-request scenarios and are not retrospectively claimed to prove arbitrary network ordering.

### Persistence and recovery boundary

Application restart with Redis still running must retain an unexpired Session. Describe Redis's own persistence separately: pin and record the chosen persistence configuration, qualify a controlled Redis restart at its documented durability boundary before claiming that scope, and state which crash/acknowledgment-loss cases remain unverified. A mounted volume alone is not a durability result.

Restoring an older store snapshot can restore an older identity state. A future restore/recovery procedure must fail closed until it reconciles that state or deliberately invalidates all pre-recovery identities through a reviewed namespace/generation boundary. Do not claim zero RPO, seamless failover, backup durability or no-resurrection across untested Redis recovery. Production operators, recovery targets, replication, Sentinel/Cluster and off-host backups remain separate, unqualified choices.
