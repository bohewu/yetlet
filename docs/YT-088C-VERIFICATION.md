## App preflight and execution identity

The Windows app adapter reuses the accepted local fixed NTFS Anchor traversal: root handle, single-component `NtCreateFile` relative opens, `OBJ_DONT_REPARSE`, volume/file IDs and denial of delete sharing for every ancestor. UNC/device/verbatim ambiguity, traversal, missing parents and reparse components fail closed. The app directory must be owned by the current token user; its owner/DACL is read from a handle opened relative to the held parent. Missing/null DACL, unsupported effective ACE forms, foreign ownership or mutating grants to untrusted principals are rejected. Only the current user, SYSTEM and Administrators may hold mutating grants; the latter two do not satisfy app/file current-user ownership. Ordinary read-only grants are permitted. This conservative policy can reject otherwise usable ACL layouts; it never changes the caller's ACL to make a build pass.

Shared `platform::fs::open_app` still reads and validates the standalone `[package]`/`[workspace]` manifest before reading the explicit existing Cargo.lock, using the unchanged UTF-8/TOML size limit and constraints. Windows retains the read handles for both regular files, denying write/delete sharing through child completion. It reopens each exact relative name and compares IDs before execution. A pre-existing incompatible write/delete opener refuses preflight. Cargo receives the same literal `build --frozen --manifest-path Cargo.toml [--release]` and the same `RUSTUP_AUTO_INSTALL=0`, `RUSTUP_SKIP_UPDATE_CHECK=1`, `CARGO_NET_OFFLINE=true` overrides. There is no implicit lock creation, online fallback or shell.

The entire Anchor chain, cwd security handle and both files live across CreateProcess, suspended-child verification, resume, leader exit and owned Job cleanup. The full cwd spelling is passed only while that complete identity chain is held. Parent/app directory rename/delete cannot replace a pinned entry. A directory containing a pinned child, manifest or lock cannot be emptied for a junction substitution; [Microsoft's reparse contract rejects nonempty directories](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4aeefef8-92c3-4abc-af7a-a610caf8a165). This does not use path canonicalization as a security fallback or change the supervisor's own cwd. Native enforcement still needs the GNU/MSVC tests below; compiler checks alone cannot establish it.

Cargo executable resolution examines only explicit absolute PATH directories for `cargo.exe`, then opens its complete ancestry and regular file through the same pinned no-reparse mechanism and checks executable owner/DACL safety. A candidate existence probe only skips absent PATH entries; it never authorizes execution. CreateProcess receives the exact vetted executable path and never searches the selected app cwd, `cmd`, batch files or PowerShell. The executable's bytes and directory entries remain pinned until cleanup. The inherited user toolchain and application build scripts are trusted inputs; this CLI is not an application sandbox, DLL-search sandbox or an isolation boundary against the same user, administrators or kernel components.

## Narrow native build process ownership

The adapter uses cached SDK declarations, not manual FFI or `Command` with an unresumable suspended thread. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) returns both owned handles. It starts the initial thread suspended, assigns the exact process handle to an unnamed non-inherited Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and no breakaway flags, confirms membership, revalidates app/executable identities, and resumes the owned primary thread exactly once. Assignment/nested-job incompatibility fails closed and terminates/reaps the exact suspended process without executing its user entrypoint. [Job ownership and descendant rules](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) apply to ordinary Cargo descendants.

Only duplicated stdin/stdout/stderr handles appear in the `STARTUPINFOEXW` inheritance allowlist. Missing headless stdio uses the native NUL device. Environment overrides are merged case-insensitively and serialized as a sorted Unicode block; arguments use Windows CRT quoting without a shell. The native Cargo exit DWORD is read from the held process handle after it signals, then represented by Windows ExitStatus without inventing a POSIX signal. Existing finalization preserves its exit bits.

After leader exit or a supervision error, cleanup terminates only the exact owned process/Job, polls ActiveProcesses to zero and waits for the held leader. Each cleanup wait has a five-second deadline; a failed cleanup is nonzero, never success. RAII also closes the non-inherited kill-on-close Job on failure or supervisor termination. A normal build has no artificial compilation timeout. No PID/name-based kill, untargeted Ctrl-C broadcast, global console handler or thread-handle workaround is introduced.

**Windows dev remains unsupported.** A vetted `dev` request is rejected before child creation by the process adapter (current shared spawn/supervision failure exit 125); invalid apps still fail preflight with exit 1. Build creates a separate process group but does not implement graceful console forwarding or claim foreground dev cancellation, terminal restoration or full headless dev behavior. Those belong to YT-088d. Public preview HELP/README retain the accepted Linux support statement pending native acceptance and the later documentation slice; this record describes candidate implementation, not a new support promise.
